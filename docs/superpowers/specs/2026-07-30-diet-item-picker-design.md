# 항목 고르기 화면 개편 · 날짜 스트립 주 이동 (iOS) 설계

작성일: 2026-07-30
선행 문서: `docs/superpowers/specs/2026-07-27-diet-tracking-ios-design.md`

같은 목적의 상용 앱들의 음식 등록 화면을 참고해 `MealItemEditView`를 다시 짜고, 하루 화면의 날짜
스트립에 주 단위 좌우 이동을 넣는다. **백엔드 변경은 없다** — 지금 있는 엔드포인트와
지금 있는 데이터로만 만든다.

## 배경

지금 항목을 담으려면 검색해서 하나 고르고, 시트를 닫고, 「음식 추가」를 다시 누르고,
또 검색한다. 상을 차려 먹은 끼니를 손으로 적으면 이 왕복을 대여섯 번 한다. 사진 없는
기록을 열어 둔 이유가 「과자 하나를 적으려고 사진을 찍게 만들지 말자」였는데, 정작
여러 항목을 적는 경로가 그만큼 번거로우면 같은 자리에서 사용자를 잃는다.

참고 화면들이 이 문제를 푸는 방식은 셋이다 — **출처별 탭**, **⊕ 한 번으로 담기**,
**하단 바에서 한꺼번에 기록**. 이 셋은 전부 지금 데이터로 만들 수 있다.

## 데이터가 허락하지 않는 것

참고 화면에는 있지만 우리가 만들 수 없는 것들이다. 나중에 「왜 빠졌지」를 다시 조사하지
않도록 근거를 남긴다.

| 참고 화면의 요소 | 못 만드는 이유 |
| --- | --- |
| 포화지방 · 트랜스지방 · 콜레스테롤 | `Food` 테이블에 컬럼이 없다. 영양소는 7개뿐(열량·탄수·단백·지방·당류·나트륨·식이섬유) |
| 「100만회 이상」 인기 배지 | 조회수·인기도 데이터가 없다 |
| 즐겨찾기(★) 탭 | 테이블도 엔드포인트도 없다 |
| 세트 · 레시피 필터 | 그런 개념이 식품DB에 없다 |
| 단위 4종(회분·개·인분·g) | 음식당 기준량이 **하나**뿐이고, 그마저 자주 비어 있다 |

셋을 더하려면 백엔드 스키마 변경과 30만 행 재적재가 필요하다. 이 설계는 **화면 구조가
이 UI가 좋은 진짜 이유**라고 보고, 영양소 세 줄은 나중 판단으로 미룬다.

우리에게는 반대로 그 화면들에 없는 **식이섬유**가 있어 영양소 표에 한 줄 더 들어간다.

## 화면 ① — 항목 고르기 (`MealItemEditView` 개편)

### 탭 셋이 항목 출처 셋과 맞는다

| 탭 | 출처 |
| --- | --- |
| 자주 드셨어요 | `GET /diet/items/frequent` |
| 검색결과 | `GET /diet/foods?q=` |
| 직접 등록 | 수기 입력 (`NutritionMath.manualItem`) |

검색어를 입력하고 확정하면 **검색결과 탭으로 자동 전환**한다. 검색창은 탭 위에 두어
어느 탭에서든 바로 검색으로 들어갈 수 있게 한다.

### 필터 칩은 `dataset`을 쓴다

`전체` · `음식`(DISH) · `원재료`(RAW) · `가공식품`(PROCESSED). 검색결과 탭에서만 보인다.

가공식품 30만 건과 원재료 523건이 섞여 나오므로 구분이 실제로 필요하다. 지금은 행마다
작은 배지를 다는 것으로 처리하고 있는데, 칩이 있으면 「조리 음식만」으로 좁힐 수 있다.

**칩은 받아 온 페이지를 앱에서 거른다.** 서버에 `dataset` 파라미터가 없기 때문이다. 그래서
한계가 하나 있다 — 상위 결과가 전부 가공식품이면 「음식」 칩이 빈 목록을 보여준다. 실제로
매칭되는 조리 음식이 있는데도 그렇다. 이를 줄이려고 검색 `size`를 20에서 **50**(서버 상한)으로
올린다(`DietService.searchFoods`가 지금 `"20"`을 박아 보낸다). 그래도 부족하면
`GET /diet/foods`에 `dataset` 파라미터를 더하는 것이 진짜 해법이고, 그건 백엔드 작업이라
이 설계 밖이다.

### 행은 세 정보를 보여준다

```
제육볶음                                   375kcal   ⊕
1인분 (250g)
──────────────────────────────────────────────────
달걀                            [원재료]   143kcal   ⊕
100g 기준
```

- **1인분을 아는 항목**(`servingSizeKnown == true`): 「1인분 (250g)」과 **1인분 기준 열량**
- **모르는 항목**: 「100g 기준」과 **100g 기준 열량**

자주 드셨어요 행은 지난번 저장한 수량이 딸려 오므로 「200g · 7회」처럼 수량과 빈도를 쓴다.

### 담기는 두 가지 속도다

- **⊕ 탭** — 기본 수량으로 즉시 담는다
- **행 탭** — 상세 시트가 열려 수량·단위를 조정한 뒤 「추가하기」

**1인분을 모르는 항목은 ⊕도 상세 시트를 연다.** 채워 넣을 기본 수량이 없기 때문이다.
서버가 보내는 `servingSizeG: 200`은 원본에 1인분 정보가 없을 때 채우는 자리채움값이라,
⊕로 조용히 담기면 달걀 한 개가 200g·312kcal로 기록된다. 200g은 1800g과 달리 **그럴듯해
보여서 사용자가 고치지 않는다.** 검색 결과의 상당수가 여기 해당한다 — 원재료 전부,
가공식품 31%, 음식 21%.

자주 드셨어요 항목은 지난번 수량이 함께 오므로 ⊕가 항상 동작한다.

### 상세 시트 (`FoodDetailSheet`)

```
제육볶음                                      ✕

1인분 = 250g
┌──────────────┐  ┌─────────────┐
│  −   1.5   + │  │  1인분   ▾  │   ← 0.5씩, 최소 0.5
└──────────────┘  └─────────────┘
                                     ← g 모드일 때만:
                                       ( 50g ) ( 100g ) ( 200g )

375 kcal   [ 일일목표 15% ]
────────────────────────────────
탄수화물                       30g
  ↳ 당류                      7.5g
────────────────────────────────
단백질                         25g
────────────────────────────────
지방                           17g
────────────────────────────────
나트륨                      1,000mg
────────────────────────────────
식이섬유                      3.8g

[            추가하기            ]
```

**단위는 둘이다** — 「1인분」과 「g」.

- **1인분 모드**: 스테퍼가 인분 수를 **0.5씩** 조절한다(최소 0.5). `quantityG = servingSizeG × 인분수`.
  표시는 「0.5인분」·「1인분」·「1.5인분」(`Double.trimmedText`)
- **g 모드**: 스테퍼가 그램을 조절하고(±25, 최소 25) 직접 입력도 된다. 25는 빠른 선택 칩과
  같은 격자라 칩으로 대강 맞추고 스테퍼로 다듬게 된다. **스테퍼 하한이 직접 입력까지 막지는
  않는다** — 더 잘게 넣고 싶으면 타이핑한다. 그 아래
  **빠른 선택 칩 「50g · 100g · 200g」**을 둔다
- **`servingSizeKnown == false`**: **g 모드로 고정**하고 단위 선택을 감춘다. 수량은 비어 있고
  「1인분 정보 없음 — 드신 양을 넣어 주세요」를 단다

**왜 0.5인가.** 「반 그릇」이 실제로 가장 흔한 조정이다. 정수 스테퍼만 두면 그때마다 g 모드로
바꿔 계산해야 한다. 배수는 있는 숫자에 곱하는 것이라 없는 데이터를 지어내지 않는다.

**왜 빠른 선택 칩인가.** 1인분을 모르는 항목은 지금 반드시 타이핑해야 하는데, 검색 결과의
상당수가 여기 해당한다(원재료 전부·가공식품 31%·음식 21%). 칩 세 개가 그 타이핑을 대부분
없앤다. g 모드에서만 보이므로 1인분을 아는 항목의 화면을 어지럽히지 않는다.

### 단위를 더 늘릴 수 없는 이유

참고 화면은 오이에 「회분(1/3개)·개·인분·g」 네 단위를 준다. 우리는 못 준다 — **원본에 개당
중량이 없다.** 확인한 사실을 남겨 둔다(2026-07-30, 공공데이터포털 원본 직접 확인):

| 컬럼 | 상태 |
| --- | --- |
| `1인(회)분량 참고량` | **표본 300행 중 0행 채워짐** — 판본에서 비었다 |
| `식품중량` | 채워져 있으나 `1640g`·`930g`처럼 한 솥 분량이 섞인다 (그래서 500g 초과는 결측 처리) |
| `영양성분함량기준량` | 전부 `100g` — 영양소 기준일 뿐 단위가 아니다 |

가공식품 166개 컬럼에도 수량 관련은 이 둘뿐이다. 즉 **음식당 근거 있는 중량은 `servingSizeG`
하나**이고, 「개」·「공기」·「컵」을 만들려면 없는 환산을 지어내야 한다. 「1컵 = 200g」 같은
일반값은 쌀과 기름에 같이 적용되어 조용히 틀린 수치를 만든다 — 이 도메인이 계속 막아 온
바로 그 실패다.

사용자가 「내 밥공기 = 210g」을 직접 정하게 하는 것이 유일하게 정직한 경로이고, 저장이
붙으므로 별도 설계 대상이다(「범위 밖」 참조).

영양소는 `NutritionMath.item(from:quantityG:)`가 계산한다 — 서버의 환산식(`per100g × quantityG / 100`)과
같은 한 곳이고, 이미 테스트로 고정돼 있다.

**「일일목표 N%」는 `NutritionProfile.targetKcal` 대비 비율**이다(`round(kcal / targetKcal × 100)`).
프로필이 없으면 배지를 감춘다 — 목표가 없으면 비율에 의미가 없다.

**시트는 두 출처를 받는다** — 검색 결과(`Food`, 100g당 값)와 자주 드셨어요(`FrequentItem`,
저장된 절대값). 자주 드셨어요 항목에는 1인분 정보가 없고 저장된 영양소만 있으므로 수량이
지난번 값으로 채워진 **g 모드로 뜨고, 수량을 바꾸면 비례 환산**한다(`NutritionMath.rescaled`).
검색 결과는 100g당 값에서 환산한다(`NutritionMath.item(from:quantityG:)`). 두 경로가 쓰는
함수가 다르므로 시트는 출처를 구분해 들고 있어야 한다.

### 다중 선택은 새 끼니를 만들 때만

시트가 열리는 자리가 셋이고 성격이 다르다.

| 여는 곳 | 모드 | 이유 |
| --- | --- | --- |
| `MealConfirmView` 「음식 추가」 | **여러 개** | 아직 저장 전이라 모아서 담아도 왕복이 없다 |
| `MealConfirmView` 항목 교체 | 한 개 | 교체 대상이 하나로 정해져 있다 |
| `MealDetailView` 추가·교체 | 한 개 | 이미 저장된 끼니를 고치는 자리라 한 번에 하나씩 확인하며 바꾸는 편이 안전하다. 다중 선택은 범위 밖으로 뒀다(「범위 밖」 참조) |

여러 개 모드에서만 하단 바가 뜬다:

```
[            3개 담기            ]
```

**끼니 종류 피커는 하단 바에 두지 않는다.** 참고 화면은 그 시트가 기록 흐름의 전부라
끼니 종류가 필요하지만, 우리는 바로 뒤 `MealConfirmView`가 그 피커를 이미 갖고 있다.
둘 다 두면 같은 값을 만지는 컨트롤이 한 화면에 둘 생긴다.

담은 항목은 행에 「담김 N」 배지로 표시하고, 다시 눌러 더 담을 수 있다(같은 음식 2인분).
이 배지와 하단 바는 **여러 개 모드에서만** 나타난다.

**한 개 모드는 고르는 즉시 닫힌다** — ⊕를 누르거나 상세 시트에서 「추가하기」를 누르면
그 항목 하나를 `onCommit`으로 넘기고 시트를 닫는다. `.replace`도 같은 동작이고, 호출부가
받은 항목으로 대상을 교체한다.

### 인터페이스 변경

```swift
enum MealItemPickMode: Equatable {
    case replace(MealItemRequest)   // 교체 — 한 개
    case addOne                     // 한 개 담기
    case addMany                    // 여러 개 담기
}

MealItemEditView(
    mode: MealItemPickMode,
    service: any DietServing = DietService(),
    onCommit: ([MealItemRequest]) -> Void
)
```

`onCommit`은 **항상 배열**이다. `replace`·`addOne`에서는 원소가 하나다. 호출부가 두 모양을
구분하지 않아도 되고, 나중에 다른 화면에 다중 선택을 열 때 시그니처가 안 바뀐다.

기존 `current: MealItemRequest?`는 `.replace` / `.addOne`으로 갈라져 사라진다.

### 기존 컴포넌트

`FrequentItemList`(가로 스트립)는 **그대로 둔다.** `DietStatsView`의 「자주 먹은 음식」이
쓰고 있고 그쪽 용도에는 맞는다. 이 화면은 세로 목록이라 새 행 컴포넌트(`FoodPickRow`)를
만들어 세 탭이 공유한다.

## 화면 ② — 날짜 스트립 주 단위 이동

좌우 스와이프로 **보이는 주만 넘기고 선택 날짜는 그대로 둔다.** 날짜는 탭해야 바뀐다.

스와이프가 곧 선택 변경이면 주를 세 번 넘기는 동안 조회가 세 번 나가고 화면이 매번
갈아엎힌다. 보이는 주와 선택 날짜를 분리하면 스와이프에 네트워크가 붙지 않고, 실제로 볼
날을 정했을 때만 조회가 나간다.

### 상태

`DietDayViewModel`에 보이는 주의 기준일(`visibleWeekAnchor`)을 둔다. `weekDates`는 이제
`selectedDate`가 아니라 이 값에서 파생된다.

- `showPreviousWeek()` / `showNextWeek()` — 기준일을 ±7일 옮긴다. **네트워크 호출 없음**
- `select(_:)` — 기존 동작에 더해 기준일을 그 날짜의 주로 맞춘다(탭하면 둘이 다시 일치)
- `goToToday()` — 오늘을 선택하고 기준일도 오늘 주로 맞춘다
- `isViewingSelectedWeek` — 보이는 주에 선택 날짜가 있는지
- `visibleMonthText` — 「7월」

### 화면

스트립 위에 월 표시를 둔다. 보이는 주에 선택 날짜가 없으면 **「오늘」 버튼**을 띄운다 —
몇 주를 넘긴 뒤 돌아올 길이 필요하다.

스와이프는 `DragGesture`로 받고, 가로 이동이 임계값(50pt)을 넘고 세로 이동보다 클 때만
주를 넘긴다. 세로 스크롤(`ScrollView`)과 충돌하지 않게 하려는 조건이다.

## 테스트

`WooriHaruTests/DietConfirmTests.swift`(항목 고르기)와 `DietDayTests.swift`(날짜 스트립)에 붙인다.

**항목 고르기**

- 단위 환산 — 1인분 모드에서 인분 수를 올리면 `quantityG = servingSizeG × 인분수`이고
  영양소 7개가 함께 환산되는지
- **0.5인분** — 250g짜리 1인분에서 한 번 내리면 125g이 되고 열량도 절반인지. 최소 0.5에서
  더 내려가지 않는지(0이 되면 영양소가 0으로 굳는 기존 결함과 같은 자리다)
- **빠른 선택 칩** — g 모드에서 「100g」을 누르면 수량이 100이 되고 영양소가 따라오는지,
  1인분을 아는 항목의 1인분 모드에서는 칩이 안 보이는지
- `servingSizeKnown == false` — g 모드로 고정되고 단위 선택이 없으며 수량이 비어 있는지
- ⊕ 동작이 갈리는지 — 1인분을 아는 항목은 즉시 담기고, 모르는 항목은 상세 시트를 여는지
- 「일일목표 %」 — 프로필이 있으면 `targetKcal` 대비 비율, 없으면 감추는지
- 다중 선택 — `.addMany`에서 세 개를 담으면 `onCommit`이 원소 3개 배열을 넘기는지
- 모드별 하단 바 — `.addOne`·`.replace`에서는 안 뜨는지
- 필터 칩 — `dataset`으로 거르는지, 「전체」가 원본 그대로인지
- **주의 영양소 3필드가 새 경로에서도 살아 있는지** — 상세 시트와 ⊕ 즉시 담기 양쪽에서
  당류·나트륨·식이섬유가 `MealItemRequest`까지 오는지. 서버가 빠진 값을 조용히 0으로
  저장하므로 경로가 늘 때마다 이 확인이 따라붙어야 한다

**날짜 스트립**

- `showNextWeek()`가 `weekDates`를 7일 뒤로 옮기고 **`selectedDate`는 그대로**인지
- 주를 넘겨도 **서비스 호출이 없는지**(`fetchedDates`가 안 늘어나는지)
- `select(_:)`가 기준일을 그 날짜의 주로 맞추는지
- `goToToday()`가 선택과 기준일을 함께 오늘로 되돌리는지
- `isViewingSelectedWeek`가 넘긴 뒤 false, 돌아오면 true인지

## 범위 밖

즐겨찾기 · 인기도 · 세트/레시피 · `GET /diet/foods`의 `dataset` 파라미터 · 바코드 인식 ·
`MealDetailView`의 다중 선택.

**사용자 정의 단위**(「내 밥공기 = 210g」) — 「개」·「공기」·「컵」을 정직하게 만드는 유일한
길이지만 저장할 곳이 필요하다(서버 테이블·엔드포인트). 별도 설계로 뺀다.

**포화지방산 · 트랜스지방산 · 콜레스테롤** — 앞선 판단을 정정한다. **원본 세 종류에 모두
들어 있다**(음식 52컬럼·원재료 55컬럼·가공식품 166컬럼, 2026-07-30 직접 확인). 지금 없는
이유는 정제 스크립트가 8개 컬럼만 남기기 때문이다. 넣으려면 `build-food-csv.py` 수정 →
세 데이터셋 재정제 → `Food`·`FoodResponse`에 컬럼 3개 → `delete from food` 후 재적재(30만 행)가
필요하고, 끼니에 저장·합산까지 하려면 `MealItem`·`MealItemRequest`·하루 합계와 LLM 인식
스키마까지 번진다. **화면 개편과 독립이므로 이 설계에서 분리한다.**
