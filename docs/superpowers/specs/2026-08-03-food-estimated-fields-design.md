# 추정으로 채운 영양소 표시 (iOS) 설계

작성일: 2026-08-03
짝 저장소: `toy-back` — **서버는 이미 배포 준비가 끝났다**(`develop` `159c97a`).
설계 근거는 `toy-back/docs/superpowers/specs/2026-08-02-food-nutrition-provenance-design.md`.

## 배경

서버가 `GET /diet/foods` 응답에 필드 하나를 더했다.

```json
{ "name": "리아 두툼새우", "carbsPer100g": 18.31, "estimatedFields": ["carbs", "fat"] }
```

**한 행 안에서 공식값과 추정값이 섞여 있다는 뜻이다.** 프랜차이즈 영양성분표는
어린이 기호식품 의무표시 항목(열량·단백질·나트륨·당류·포화지방)만 싣기 때문에
탄수화물과 총지방이 아예 없고, 서버가 잔여 열량에서 계산해 채운다.

같은 배포로 음식DB가 **6,090 → 18,923행**이 됐다. 버려지던 13,405행을 되살린 것인데
그 대부분도 탄·지가 추정이다. 즉 **검색 결과의 상당수에 이 필드가 붙는다** —
피자 4,227 · 커피 1,647 · 스무디 1,011 · 라떼 904, 브랜드로는 파파존스 528 ·
뚜레쥬르 456 · 피자헛 373 · 스타벅스 192가 새로 나온다.

**지금 깨지는 건 없다.** Swift `Codable`은 모르는 키를 무시한다. 다만 사용자가
「탄수화물 48g」을 보면서 그게 공식값인지 계산값인지 알 방법이 없다.

## 계약

| 필드 | 형 | 뜻 |
| --- | --- | --- |
| `estimatedFields` | `[String]` | 서버가 채운 필드. 빈 배열이면 전부 원본 값 |

값은 `"carbs"` / `"protein"` / `"fat"` 셋뿐이다. **`"protein"`은 실제로는 안 온다** —
원본에 단백질이 없는 행은 서버가 아예 버린다. 그래도 서버가 열어 둔 값이라 앱도 받아 둔다.

`GET /diet/foods`에만 있다. 자주 드셨어요(`FrequentItem`)와 사진 인식 항목에는 없다 —
저장된 `MealItem`에서 오는데 거기에는 이 값을 싣지 않는다(`badge`·`maker`와 같은 이유).

## ⚠️ 먼저 읽을 함정 셋

### 함정 1 — **옵셔널로 받는다.** non-optional로 받으면 배포 순서가 묶인다

```swift
let estimatedFields: [String]?   // ← 옵셔널이어야 한다
```

`Food`가 배열로 디코딩되므로 **한 건이라도 키가 없으면 `[Food]` 전체가 실패**하고 검색
화면이 빈 목록이 된다. non-optional로 받으면 **서버가 배포되기 전에 앱이 나가는 순간
검색이 죽는다.**

`2026-08-02-diet-food-search-catchup-design.md`가 영양소 3종을 non-optional로 받아
배포 순서를 묶어 둔 자리다. 그때는 서버를 먼저 내보내는 것으로 넘어갔지만, 이번엔
옵셔널이면 순서를 신경 쓸 필요가 없다.

빈 배열과 `nil`을 화면에서 구분하지 않는다 — 둘 다 「추정 없음」이다.

### 함정 2 — 배지를 **행마다** 달아야 한다. 시트 전체에 달면 거짓말이 된다

`estimatedFields`가 `["fat"]`인 행이 647건 있다(탄수화물은 원본, 지방만 추정).
그 반대도 105건이다. 상세 시트 맨 위에 「이 음식은 추정값입니다」를 한 번 다는 방식이면
**공식값인 탄수화물까지 의심받는다.**

**→ `NutrientRow`에 `isEstimated`를 둔다.** 지금 `isSub`가 붙어 있는 그 자리다.

```swift
struct NutrientRow: Identifiable, Equatable {
    let name: String
    let valueText: String
    let isSub: Bool
    /// 서버가 잔여 열량에서 계산해 채운 값. 틀렸다는 뜻이 아니라 **출처가 다르다**는 뜻이다.
    let isEstimated: Bool
    var id: String { name }
}
```

탄수화물·지방 두 줄만 이 값이 참일 수 있다. 당류·나트륨·식이섬유·포화지방·트랜스지방·
콜레스테롤은 **서버가 출처를 기록하지 않으므로 항상 거짓이다** — 모르는 것을 모른다고
두는 것이지, 원본 값이라는 뜻이 아니다.

### 함정 3 — 목록 행에는 달지 않는다

`FoodPickRow`는 이미 `badge`(데이터셋)와 `brandText`(브랜드) 두 개를 달고 있고,
이름이 `피자_뉴욕 오리진 피자 오리지널 (L)`처럼 길어 세 번째를 넣을 자리가 없다.

**검색 결과 대부분에 붙는 표시라 목록에 달면 정보가 아니라 소음이 된다** — 되살린
12,833행이 전부 해당한다. 수량을 정하려고 상세 시트를 여는 순간에만 보이면 된다.

## 해야 할 일

### 1. `Food` — 필드 하나

```swift
struct Food: Codable, Hashable, Identifiable {
    // ...
    /// 서버가 잔여 열량에서 계산해 채운 필드(`["carbs","fat"]`). 비었으면 전부 원본 값이다.
    ///
    /// 프랜차이즈 영양성분표는 어린이 기호식품 의무표시 항목(열량·단백질·나트륨·당류·
    /// 포화지방)만 싣는다. 탄수화물·총지방이 아예 없어서 서버가 같은 분류의 음식에서
    /// 탄:지 비율을 빌려 채운다.
    ///
    /// **옵셔널이다** — non-optional로 받으면 서버 배포 전에 앱이 나가는 순간 검색 결과
    /// 배열 전체가 디코딩에 실패한다(함정 1).
    let estimatedFields: [String]?
}
```

### 2. `FoodPickSource` — 조회 함수

```swift
/// 이 영양소가 추정으로 채워진 값인가. **검색 결과에만 있다** — 자주 드셨어요는 저장된
/// 항목이라 출처를 모른다(`badge`·`brandText`와 같은 이유).
func isEstimated(_ field: String) -> Bool {
    switch self {
    case let .food(food): food.estimatedFields?.contains(field) == true
    case .frequent: false
    }
}
```

`.frequent`에서 `false`인 것은 **「원본 값」이라는 뜻이 아니라 「모른다」는 뜻이다.**
저장된 항목의 출처를 되짚을 방법이 서버에도 없다.

### 3. `FoodDetailViewModel.nutrientRows` — 두 줄에만 표시

`isEstimated`를 `NutrientRow`에 더하고, 탄수화물·지방 두 줄에만 `source.isEstimated(...)`를
넣는다. 나머지 줄은 `false` 고정.

지금 이 파일에 커밋 안 된 변경이 있다(`fatDetailRows` 추가). **그 위에 얹는다.**

### 4. `FoodDetailSheet` — 배지

`row.isSub` 분기가 있는 `HStack`에 한 조각 더한다. 값 옆에 작은 라벨이면 된다.

```swift
Text(row.valueText)
if row.isEstimated {
    Text("추정")
        .font(.caption2)
        .foregroundStyle(Color.slate400)
        .padding(.horizontal, 4).padding(.vertical, 1)
        .background(Color.slate100, in: Capsule())
}
```

**문구는 「추정」이다.** 「부정확」·「주의」처럼 값을 깎아내리는 말을 쓰지 않는다 —
서버 실측에서 이 추정의 오차가 **그 음식을 아예 못 찾던 지금보다 나쁘지 않다.** 사용자가
알아야 할 것은 값이 틀렸다는 게 아니라 **출처가 다르다**는 것이다.

시트 어딘가에 한 줄 설명을 둔다. 배지만으로는 무슨 뜻인지 알 수 없다:

> 브랜드가 공개하지 않아 열량에서 계산한 값이에요.

## 테스트

- **키가 없는 JSON도 디코딩된다** — `estimatedFields`가 통째로 빠진 응답으로 고정.
  **함정 1이 재현되는 자리다.** 이 테스트가 없으면 non-optional로 바꿔도 통과한다
- **한쪽만 추정한 행** — `["fat"]`일 때 지방 줄에만 배지가 붙고 탄수화물 줄에는 안 붙는지.
  *두 줄에 똑같이 붙이면 빨개져야 한다*(함정 2)
- **모르는 값이 섞여 와도 죽지 않는다** — `["carbs","calcium"]`을 디코딩해 탄수화물에만 붙는지
- **`.frequent`는 항상 false** — 자주 드셨어요 항목의 모든 줄에 배지가 없는지
- **표시 전용 영양소에는 안 붙는다** — 당류·나트륨·포화지방 줄이 `isEstimated == false`인지
- 기존 상세 시트 테스트가 그대로 통과하는지

**고의 파손 확인을 권한다.** `estimatedFields`를 non-optional로 바꾸면 첫 테스트가,
`isEstimated`를 시트 전체 플래그로 만들면 두 번째가 실제로 빨개져야 한다.
**두 저장소 모두 「구현이 망가져도 통과하는 테스트」로 여러 번 데였다.**

## 배포 순서

**아무 순서나 된다.** `estimatedFields`가 옵셔널이라 서버가 안 줘도 nil이고, 서버가 먼저
나가도 앱은 무시한다.

다만 서버 쪽은 **DB 재적재를 해야 값이 붙는다.**

```sql
delete from food where dataset = 'DISH';
delete from food where code like 'MANUAL-%';
```

안 하면 `estimatedFields`가 전부 빈 배열로 와서 배지가 한 번도 안 뜬다 — 앱이 잘못된 게
아닌데 잘못된 것처럼 보인다. 배지가 안 보이면 **먼저 서버 재적재를 확인한다.**

확인용: `GET /diet/foods?q=파파존스`가 528건 근처를 주고 `estimatedFields`에
`["carbs","fat"]`이 있어야 한다. 지금까지는 **0건**이었다.

## 곁들여 확인할 것 — 검색 결과가 3.1배가 됐다

서버가 정렬에 「추정 없는 행 먼저」를 넣었지만, 앱에서 확인해 볼 만한 것이 있다.

- 「피자」로 검색하면 되살린 4,227행이 쏟아진다. 상위 50건이 쓸 만한지
- 「도미노」·「파파존스」·「스타벅스」가 이제 결과를 주는지
- 롯데리아는 공공데이터 83건 + 수동 등록 56건인데 **서버가 중복 29건을 이미 뺐다.**
  같은 버거가 두 번 보이면 서버 쪽 문제이니 알려 달라

## 범위 밖

- **자주 드셨어요·사진 인식 항목의 출처 표시** — 서버가 `MealItem`에 안 싣는다
- **목록 행 배지**(함정 3)
- **추정값을 쓴 끼니의 점수를 다르게 표시하기** — 서버 실측상 근거가 없다
- **사용자가 값을 고쳐 서버에 돌려주기** — 별도 설계(사용자 직접 등록)
