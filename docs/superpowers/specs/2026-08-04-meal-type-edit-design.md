# 저장된 끼니의 타입 수정 (iOS + 서버) 설계

작성일: 2026-08-04
짝 저장소: `toy-back` — **서버가 먼저 나가야 한다.** 서버 설계는 그쪽
`docs/superpowers/specs/2026-08-04-meal-type-edit-design.md`에 따로 있다. 이 문서는 **앱만** 다룬다.

## 배경

**저녁을 먹고 간식으로 저장하면 되돌릴 길이 없다.** 확정 화면에는 끼니를 고르는 Picker가
있는데(`MealConfirmView:81`), **저장 뒤에는 상세 화면의 제목으로만 보이고 바꿀 수 없다**
(`MealDetailView`의 `navigationTitle`).

지금 할 수 있는 것은 끼니를 통째로 지우고 다시 만드는 것뿐인데, **앱에 사진 바이트가 없어
사진을 다시 올릴 수 없다.** 찍어 둔 사진이 사라진다.

## 서버를 고쳐야 하는 이유

`/diet/meals`에 있는 것은 확정(`POST`)·조회(`GET`)·항목 교체(`PUT /{id}/items`)·삭제
(`DELETE`)뿐이다. **타입을 바꾸는 길이 없다.**

`Meal.mealType`은 컬럼 자체가 `var`이고 유니크 제약도 없다(인덱스만 `user_id, date`). 엔드포인트
하나를 여는 일이고, 스키마 변경은 없다.

## ⚠️ 먼저 읽을 함정 셋

### 함정 1 — **방향에 따라 동작이 다르다**

`MealType.mergesWithinDay`가 간식만 `false`다. 그래서:

| 바꾸는 방향 | 그날 대상 타입이 이미 있으면 |
| --- | --- |
| 간식 → 저녁 | **합쳐진다** (항목·사진이 저녁으로 옮겨지고 간식 끼니가 사라진다) |
| 저녁 → 간식 | **안 합쳐진다** (간식 카드가 둘이 된다) |

**이것이 이 기능의 가장 헷갈리는 지점이다.** 「오전 과자와 밤 아이스크림을 한 카드에 합치면
끼니 점수가 뒤섞인다」는 기존 판단(`MealType.mergesWithinDay` 주석)을 그대로 따르므로 비대칭이
맞지만, 구현하는 쪽이 「합치기」를 대칭으로 생각하면 틀린 코드를 쓴다.

### 함정 2 — **합쳐지면 보던 끼니의 id가 사라진다**

합침은 대상 끼니로 항목·사진을 옮기고 **원래 끼니를 지우는** 방식이다. 상세 화면이 들고 있던
`mealId`가 그 순간 죽는다. 응답을 `204 No Content`로 두면 앱이 그 사실을 알 수 없어, 화면이
사라진 끼니를 다시 조회하다 404를 받는다.

**→ `Location` 헤더에 살아남은 끼니를 가리킨다.** 본문에 담지 않는 이유는 아래 「응답」 참조.

### 함정 3 — **타입은 점수에 안 들어가고 피드백에는 들어간다**

`DietScoreCalculator`는 `mealType`을 쓰지 않는다 — 타입만 바뀌면 점수를 다시 매길 이유가 없다.
반면 `DietFeedbackPrompts`는 쓴다(`[이번 끼니] ${meal.mealType}`). 「간식치고 양이 많다」로 쓰인
피드백이 저녁으로 바뀐 뒤에도 남으면 **글이 화면과 어긋난다.**

**→ 점수는 합칠 때만 다시 계산하고(항목이 늘어나므로), 피드백은 값이 실제로 바뀔 때 다시 만든다.**

## 서버 계약

### `PATCH /diet/meals/{id}`

요청 본문:

```json
{ "mealType": "DINNER" }
```

응답:

```
200 OK
Location: /diet/meals/42
```

`Location`이 가리키는 것은 **살아남은 끼니**다. 합쳐졌으면 대상 끼니이고, 아니면 요청한 id
그대로다. **본문은 비운다.**

**본문 대신 헤더인 이유는 이 저장소의 관례다.** 끼니 확정·분석 생성·사진 업로드가 전부
`@ResponseCreated("/diet/meals/{id}")`로 `Location`에 id를 싣고, 앱의 `APIClient.postCreated`가
그것을 읽는다. 본문 봉투(`DataResponseBody`)는 **데이터를 돌려줄 때만** 쓴다 — id 하나를 위해
새 응답 DTO를 만들 이유가 없다.

의미도 이쪽이 정확하다. 「이 요청의 결과로 볼 리소스는 여기」라는 뜻이라, **원래 리소스가
사라진 상황**에 특히 맞는다(303 See Other의 정신).

**상태코드는 201이 아니라 200이다.** 서버가 `@ResponseCreated` 애스펙트를 타지 않고 컨트롤러에서
직접 조립하기로 정했다 — 그 애스펙트는 201만 내는데 `PATCH`는 만들지 않으므로 201이 거짓말이
된다(`toy-back` 설계의 「`@ResponseCreated`를 쓰지 않는다」).

**앱은 이 차이에 손댈 것이 없다.** `APIClient.rawFetchWithResponse`가 `200...299`를 통과시키고,
`postCreated`·`patchCreated`는 **상태코드를 보지 않고 `Location` 헤더만 읽는다.** 확정·분석
생성·사진 업로드가 201로 오는 것과 이 요청이 200으로 오는 것을 앱이 구분하지 않는다.

소유권은 기존 `requireOwned`로 검사한다 — 남의 끼니 id로 타입을 바꾸는 길이 열리면 안 된다.
없는 id는 기존 `RESOURCE_NOT_FOUND`(404)를 준다.

### 세 갈래

**① 요청 타입이 지금과 같다** — 아무것도 하지 않고 요청한 id를 돌려준다. **피드백을 다시 만들지
않는다.** 앱이 실수로 같은 값을 보내도 유료 호출이 나가면 안 된다.

**② 합칠 대상이 없다** — `mealType`만 바꾼다. 대상 타입이 간식이면 항상 여기다
(`mergesWithinDay == false`). 점수는 그대로 두고 **피드백만 다시 만든다.**

**③ 합칠 대상이 있다** — 대상 타입이 `mergesWithinDay`이고 같은 날 그 타입 끼니가 이미 있는
경우다. 대상은 확정 저장과 **같은 기준**으로 고른다:

```kotlin
repository.findFirstByUserAndDateAndMealTypeOrderByCreatedAtAscIdAsc(user, date, mealType)
```

항목과 사진을 대상으로 옮기고 원래 끼니를 지운다. **점수를 다시 계산하고 피드백도 다시 만든다.**

### 합칠 때 사진 순서

**`sortOrder`는 대상의 최대값 다음부터 매긴다.** 확정 저장의 병합이 이미 그렇게 하고 있고
(`MealService.attachPhotos`), 0부터 다시 매기면 `Meal.photos`의 `@OrderBy("sortOrder asc")` 때문에
`0,1,0,1`이 되어 **앱의 사진 순서가 뒤섞인다.**

### 피드백 재생성

확정 저장·항목 교체와 같이 `runAfterCommit { feedbackGenerator.generateForMeal(살아남은 id) }`로
뒤에서 돌린다. `markFeedbackPending()`도 같이 세워 앱의 기존 폴링이 받게 한다.

## 앱 흐름

### 어디에 있나

**상세 화면 툴바의 `Menu`.** 네 타입을 나열하고 현재 타입에 체크를 둔다. 항목 수정·삭제와 같은
화면에 수정 수단을 모은다 — 잘못 들어간 끼니는 열어 보면서 알아채는 경우가 많다.

`isSaving` 중에는 잠근다. 항목 편집과 같은 이유로, 두 요청이 같은 스냅샷에서 출발하면 나중 것이
먼저 것을 덮는다.

### 보내기 전에 그날을 조회한다

고르면 곧바로 보내지 않는다. `fetchDay(date:)`로 그날 끼니 목록을 받아 **합쳐질지 먼저 판단한다.**
상세는 `meal.date`를 알고 있다.

이것은 확정 화면이 이미 하는 일과 같다(`MealConfirmViewModel.mergesIntoExisting`). 판단 결과에 따라
세 문구로 갈린다:

문구에서 **끼니 이름은 고르는 타입의 `label`로 채운다**(아침·점심·저녁·간식). 아래는 저녁을 고른
경우다.

| 상황 | 알럿 |
| --- | --- |
| 합쳐진다 | 「이미 기록한 저녁에 합쳐져요. **사진도 함께 옮겨져요.** 합쳐진 뒤에는 되돌릴 수 없어요.」 |
| 안 합쳐진다 | **알럿 없이 바로 보낸다** — 잃는 것도 놀랄 것도 없다 |
| 그날 조회 실패 | 「이미 기록한 저녁이 있다면 합쳐지고, 합쳐진 뒤에는 되돌릴 수 없어요.」 |

**「합쳐진다」와 「모르겠다」는 다른 말이다.** 확정 화면이 이 구분에 주석을 따로 남겨 뒀다
(`MealConfirmViewModel:74`) — 앞은 확정된 사실이고 뒤는 추측이라, 같은 문구를 쓰면 사용자가
확인 버튼을 누를 때 무엇을 승인하는지 모른다.

**잃는 것이 없으므로 알럿의 성격이 「경고」가 아니라 「되돌릴 수 없다」다.** 사진이 따라가기
때문이다. 다만 사진이 따라간다는 사실은 적어 준다 — 저녁 카드의 사진이 갑자기 늘어나는 것을
미리 알아야 놀라지 않는다.

### 응답을 받은 뒤

**`APIClient`에 `patchCreated`를 더한다.** `Location`에서 id를 뽑는 헬퍼가 지금은 POST 전용이다
(`postCreated`·`postMultipartCreated`). 뽑는 방식은 그대로 본뜬다 — 헤더가 없거나 끝 조각이 숫자가
아니면 `APIError.serverError`를 던진다. `MockAPIClient`도 `postCreatedResults`를 본떠 받는다.

**돌려받은 id가 원래 id와 다르면 상세를 닫고 하루로 돌아간다.** 합쳐졌으므로 보던 끼니는
없어졌다. 끼니 삭제가 이미 그렇게 `dismiss()`한다.

같은 화면을 대상 끼니로 갈아끼우는 방법도 있지만 `MealDetailView.mealId`가 `let`이라 화면 구조를
흔들어야 하고, **「합쳤다」는 사실을 화면 전환으로 느끼는 편이 정직하다** — 제목만 슬쩍 바뀌면
사용자는 자기 간식 기록이 어디 갔는지 모른다.

**닫으면서 「합쳐졌어요」를 따로 알리지 않는다.** 합침은 항상 사용자가 알럿에서 승인한 뒤에만
일어나므로 화면이 닫히는 이유를 이미 안다. 「앱이 조회했을 때는 저녁이 없었는데 그 사이 다른
기기가 저장해 몰랐던 채로 합쳐지는」 경우를 걱정할 수 있지만, **이 앱은 한 기기에서만 쓴다.**

**같으면 화면에 남는다.** 다시 조회해 제목이 「간식」에서 「저녁」으로 바뀐다.

**두 경우 모두 `onChanged()`를 부른다.** 하루 총합은 안 바뀌지만(같은 항목이 다른 카드로 갈 뿐)
카드 구성이 바뀌므로 하루 화면이 다시 조회해야 한다.

### 오류

**상세 화면의 기존 `errorMessage` 알럿을 그대로 쓴다.** 툴바 메뉴는 시트가 아니라 상세를 덮지
않으므로, 지난 수량 시트(`QuantitySaveOutcome`)처럼 실패 이유를 밖으로 들고 나올 필요가 없다.

## 경계 조건

**낡은 화면(`isStale`)에서도 받는다.** 항목 편집은 막고 있지만(「최신 상태를 불러오지 못했어요」)
그 이유는 항목을 **전체 교체**로 보내서 낡은 목록이 방금 성공한 변경을 덮어쓰기 때문이다. 타입
변경은 **항목을 아예 안 보낸다** — `mealType` 한 칸뿐이라 덮어쓸 것이 없다. 합침 판단이 낡았더라도
최종 판단은 서버가 하므로 안전하다.

**같은 타입은 앱에서 걸러 안 보낸다.** 서버도 ①로 막지만, 앱에서 먼저 끊어야 헛된 왕복이 없다.

**그 사이 끼니가 지워졌으면** 404 → 기존 「찾을 수 없습니다」 경로를 탄다.

**합치면 하루 점수·목표가 함께 움직일 수 있다.** 하루 목표는 그날 **첫 끼니의 스냅샷**에서
나오는데, 합쳐서 사라지는 쪽이 그날 첫 끼니였고 **그 사이 프로필(몸무게·목표)을 바꿨다면** 두
번째 끼니의 스냅샷이 하루 목표가 된다(`toy-back` 설계 함정 5). 서버가 「그대로 둔다」로 정한
알려진 결과다.

**앱 버그로 보이기 딱 좋은 자리라 여기 적어 둔다** — 앱은 `onChanged()`로 다시 조회할 뿐이고
값은 서버가 정한다. 프로필을 바꾼 적이 없으면 두 스냅샷이 같은 값이라 아무 일도 일어나지 않는다.

## 테스트

**판단을 뷰모델에 둔다** — 뷰에 두면 합침 분기와 조회 실패 분기가 테스트에 안 닿는다.
`MealDetailViewModel.changeMealType(_:)`이 그날 조회·판단·전송을 하고, 뷰는 알럿 문구와 닫을지
여부만 받는다.

`FakeDietService`에 `patchMealType`을 더하고 다음을 덮는다:

- 같은 타입이면 **요청이 안 나간다**
- 합쳐질 상황을 알아본다 / 안 합쳐질 상황과 구분한다
- **그날 조회 실패는 다른 문구다**(「합쳐진다」 ≠ 「모르겠다」)
- 합쳐졌으면 화면을 닫으라는 신호가 온다(돌려받은 id ≠ 원래 id)
- 안 합쳐졌으면 화면에 남고 제목이 바뀐다
- 실패하면 `errorMessage`가 차고 화면은 그대로다
- **저녁 → 간식은 합치지 않는다**(함정 1의 비대칭)

서버 쪽 테스트는 `toy-back` 몫이라 이 문서에는 계약만 적는다.

## 범위 밖

- **날짜 수정** — 어제 저녁을 오늘로 저장한 경우. 하루 집계·점수·피드백이 이틀에 걸쳐 다시
  계산돼야 해서 훨씬 크다. 별도 설계가 필요하다.
- **합친 것을 되돌리기** — 어느 항목이 어느 끼니에서 왔는지 서버가 기록하지 않는다.
- **하루 화면 카드에서 바로 바꾸기** — 상세에 있으면 충분하다. 숨은 제스처는 발견되지 않는다.
- **여러 끼니를 한 번에 옮기기**
