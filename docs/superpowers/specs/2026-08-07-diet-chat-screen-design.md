# 식단 코치 채팅 화면 (iOS) 설계

작성일: 2026-08-07
짝 저장소: `toy-back` — **서버가 먼저 나가야 한다.** 서버 설계는 그쪽
`docs/superpowers/specs/2026-08-07-diet-chat-timeline-design.md`에 따로 있다. 이 문서는 **앱만** 다룬다.

## 배경

식단 기록에 대해 **되물을 수 있는 화면이 없다.** 하루 화면은 점수·총평을 보여주고 끝이고,
「점심이 왜 47점이야?」에 답할 자리가 없다.

서버에 코치 채팅이 생긴다. 그런데 그것은 **대화창이 아니라 타임라인**이다 — 끼니를 확정하면
서버가 그 자리에 끼니 카드를 쌓고, 하루 총평이 완성되면 총평 카드를 쌓는다. 사용자 질문과
코치 답변이 그 사이에 끼어 앉는다. 처음 열어도 빈 화면이 아니다.

## ⚠️ 먼저 읽을 함정 셋

### 함정 1 — **날짜가 두 축이다**

메시지마다 값이 둘이다.

| 값 | 뜻 |
| --- | --- |
| `createdAt` | **언제** 그 일이 있었나 (물은 시각·확정한 시각) |
| `date` | **어느 날 밥** 얘기인가 |

스트림은 `createdAt` 순이다. 그래서 **8월 6일에 8월 1일을 물으면 그 말풍선은 8월 6일 자리에
앉는다.** 두 값을 같은 것으로 다루면 그 질문이 8월 6일 얘기로 읽힌다.

**→ 날짜 구분선은 `createdAt`, 말풍선 배지는 `date`.** 그리고 **배지는 둘이 다를 때만** 붙인다.
같은 날 얘기를 같은 날 하는 경우가 대부분이라 늘 붙이면 노이즈가 되고, 안 붙이면 과거 날짜
질문이 정체 없이 앉는다.

카드도 마찬가지다. 8월 1일 끼니를 8월 3일에 뒤늦게 확정하면 카드는 8월 3일 자리에 앉고
배지가 `08-01`이다.

### 함정 2 — **보고 있던 날짜와 스트림 맨 아래가 다르다**

플로팅 버튼을 누른 순간의 날짜가 질문의 앵커다. 그런데 8월 1일을 보다가 열면 **스트림 맨
아래는 최근 대화**이고 8월 1일 카드는 저 위에 있다. 사용자는 자기가 지금 어느 날에 대해
묻는 중인지 알 수 없다.

**→ 입력창 위에 앵커 칩을 고정한다** — 「8월 1일에 대해 묻는 중」. 칩의 `✕`를 누르면 앵커가
**오늘로** 돌아간다(그때 칩은 사라진다 — 오늘이 기본값이라 늘 띄우면 자리만 먹는다).

그 날짜 카드로 자동 스크롤하지 않는다. 첫 페이지에 그 카드가 없을 수도 있고(그날 이후 대화가
많으면), 채팅앱이 맨 아래에서 열리지 않으면 그 자체로 낯설다.

### 함정 3 — **모르는 `type`이 온다**

서버가 카드 종류를 늘리면(활동 에너지·몸무게 카드는 서버 설계의 「범위 밖」에 있다) 옛 앱에
모르는 `type`이 내려온다. `enum`을 그냥 디코딩하면 **그 자리에서 페이지 전체가 실패한다.**

**→ `MessageType`에 `unknown` 케이스를 두고 그 메시지는 건너뛴다.** `FoodDataset.unknown`이
이미 같은 이유로 있다.

## 서버 계약 (앱이 쓰는 만큼만)

### `GET /diet/chat?before=&size=`

최신이 먼저 온다(`id DESC`). 앱이 뒤집어 아래에 붙인다. `nextCursor`가 null이면 더 없다.

```swift
struct ChatMessage: Decodable, Identifiable {
    let id: Int
    let type: ChatMessageType   // text | mealCard | daySummary | unknown
    let date: String            // "2026-08-01" — 어느 날 밥 얘기인가
    let role: ChatRole          // user | assistant
    let createdAt: String       // 서버 LocalDateTime 문자열 — 아래 「이탈」 참조
    let content: String?        // text일 때만
    let meal: ChatMealCard?     // mealCard일 때만
    let day: ChatDayCard?       // daySummary일 때만
}
```

`content`가 **nullable이 됐다.** 지금 앱에는 채팅 코드가 없어 깨질 화면은 없지만, 이것이 이
API의 파괴적 변경이라 서버가 먼저 나가야 하는 이유다.

카드 필드는 서버 설계의 `ChatMealCard` / `ChatDayCard`를 그대로 따른다. 앱이 쓰는 것:

- **끼니 카드** — `mealType` · `score` · `scoreBasis` · `totalKcal` · 탄단지 g · `photoUrl` · `feedback`
- **총평 카드** — `dayScore` · `totalKcal` · `targetKcal` · `feedback`

`targetKcal`은 그날 첫 끼니의 스냅샷이다. 프로필의 현재 목표가 아니라서, 몸무게를 바꿔도
과거 카드의 분모가 흔들리지 않는다.

**`scoreBasis`의 `percent`를 그대로 쓴다.** 구성비 막대(`46% / 17% / 37%`)를 g에서 직접 계산하지
않는다 — 비율의 분모가 `totalKcal`이 아니라 매크로에서 역산한 값이라 순진하게 나누면 다른
숫자가 나온다. `ScoreBasisCard`가 이미 같은 이유로 「앱은 계산하지 않는다」를 지킨다.

### `POST /diet/days/{date}/chat`

본문 `{ "message": "..." }`, 응답은 **저장된 답 한 건**(`ChatMessage`, `type == .text`)이다.
질문 행도 서버가 함께 저장하지만 응답에는 답만 온다 — 질문은 앱이 이미 갖고 있다.

**LLM 호출이라 느리다.** 응답까지 수 초가 걸린다.

**빈 날은 400이다.** 그날 기록된 끼니가 없으면 서버가 거절한다. 앱이 먼저 막는다(아래).

## 화면

### 진입

식단 홈(`DietHomeView`) 오른쪽 아래 플로팅 버튼. `overlay`에 얹는다 — 하루 화면이 이미
`.overlay`를 쓰고 있다.

**보고 있던 날짜를 그대로 앵커로 넘긴다.** `DietHomeView`가 그 날짜를 갖고 있다.

### 구조

```
┌──────────────────────────────┐
│  ‹      식단 코치             │  navigationTitle
├──────────────────────────────┤
│                              │
│  ── 2026-08-06 ──────────    │  날짜 구분선 (createdAt)
│                              │
│  ┌────────────────────────┐  │

│  │ ▓▓▓▓▓▓▓▓░░░░▒▒▒▒       │  │  구성비 스택 (scoreBasis.percent)
```

**코치 이름·아바타를 두지 않는다.** 서버 설계가 「이름·캐릭터를 두지 않는다」로 정했다 —
이름을 붙이면 말투의 일관성을 계속 맞춰야 하고, 얻는 것이 그것뿐이다.

**말풍선은 좌우 정렬로 가른다.** `role == .user`가 오른쪽, `.assistant`와 카드가 왼쪽이다.

**카드는 `GlassCard`를 쓴다.** 이 앱의 디자인 시스템이다(`2026-06-28-ios26-liquid-glass-foundation-design.md`).

### 빈 날 잠금

`DailyDiet.meals`가 비었으면 **입력창을 잠그고** 「이 날은 기록이 없어서 물어볼 것이 없어요」를
띄운다. 서버도 400으로 막지만, 플로팅 버튼이 늘 떠 있어서 기록 전에 누르는 일이 흔하다.
그때마다 오류 알럿을 띄우면 곤란하다.

**스트림은 그대로 보여준다.** 과거 대화를 읽는 데는 문제가 없다.

### 무한 스크롤

맨 위에 닿으면 다음 장을 부른다. `nextCursor`가 null이면 멈춘다.

**로딩 중에 또 부르지 않는다.** `isLoadingPage` 가드 하나로 막는다 — 스크롤이 위쪽에 머무는
동안 `onAppear`가 여러 번 뜬다.

**다음 장을 붙일 때 스크롤 위치를 유지한다.** 위에 붙이면 콘텐츠가 밀려 사용자가 읽던 자리가
튄다. `ScrollViewReader`로 이전 첫 메시지 id에 앵커를 잡는다.

### 전송

- **전송 중에는 입력창을 잠근다** — `MealConfirmViewModel.isSaving`과 같은 가드
- **낙관적으로 내 말풍선을 먼저 붙인다.** LLM이 수 초 걸려서, 안 붙이면 내가 뭘 보냈는지
  화면에서 사라진다
- 답을 기다리는 동안 **코치 자리에 로딩 말풍선**을 둔다
- **실패하면 내 말풍선을 남기고 「보내지 못했어요 · 다시 시도」를 붙인다.** 지우면 사용자가
  다시 타이핑해야 한다. 서버는 실패 시 아무것도 저장하지 않으므로(질문·답을 한 트랜잭션에
  쓴다) 재시도가 안전하다

### 생성 중인 문장

- **끼니 카드의 `feedback`이 null** — 「코치가 보고 있어요」. 재시도 버튼을 두지 않는다.
  끼니를 고치면 자연히 다시 만들어진다(하루 화면이 이미 같은 판단을 한다)
- **총평 카드의 `feedback`이 null** — 「마감 피드백을 만들고 있어요」. `DietHomeView.feedbackSection`과
  **같은 문구를 쓴다.** 두 화면이 같은 상태를 다르게 말하면 사용자는 다른 일이 일어났다고 읽는다

**폴링하지 않는다.** 화면을 다시 열면 채워져 있다. 채팅에 폴링을 붙이면 페이지 전체를 다시
받아야 해서 값이 크다.

## 구조

| 파일 | 책임 |
| --- | --- |
| `Models/DietChat.swift` | `ChatMessage` · `ChatMessageType` · `ChatRole` · `ChatMealCard` · `ChatDayCard` |
| `ViewModels/DietChatViewModel.swift` | 페이징·전송·낙관적 말풍선·잠금 판단·행 조립 |
| `Views/Diet/DietChatView.swift` | 스트림·입력창·앵커 칩 |
| `Views/Diet/Components/ChatMealCardView.swift` | 끼니 카드 |
| `Views/Diet/Components/ChatDayCardView.swift` | 총평 카드 |
| `Views/Diet/Components/ChatBubble.swift` | 말풍선 + 날짜 배지 |
| `Views/Diet/Components/MacroStackBar.swift` | 구성비 스택 막대 |

**`MacroStackBar`는 새로 만든다.** 기존 `MacroBar`는 **목표 대비** 막대라 다른 것이다 —
이름이 비슷해 재사용하려다 `2509kcal 중 80g`처럼 뜻이 맞지 않는 화면이 나오기 쉽다.

`DietServing`에 둘을 더한다:

```swift
func fetchChatPage(before: Int?, size: Int) async throws -> ChatPage
func askChat(date: String, message: String) async throws -> ChatMessage
```

**`FakeDietService`에도 함께 더한다.** 프로토콜에 기본 구현을 두지 않는다 — 두면 기존
호출부가 그대로 컴파일되어 「고쳤는데 안 부르는」 상태가 조용히 남는다(`searchFoods`의
`dataset` 주석과 같은 이유).

**판단은 전부 뷰모델에 둔다.** 배지를 붙일지, 구분선을 어디서 끊을지, 입력창을 잠글지가 뷰에
있으면 테스트가 못 닿는다.

## 테스트

`WooriHaruTests`에 `DietChatTests.swift`. 기존 `FakeDietService` 패턴을 그대로 쓴다.

**날짜 두 축**
- `date`가 구분선 날짜와 **다르면** 배지가 붙는다
- **같으면 안 붙는다** — 늘 붙이는 구현이면 여기서 빨개진다
- 날짜 구분선이 `createdAt` 기준이다 — `date`만 다른 메시지 둘이 **한 구분선 아래** 있는지

**페이징**
- 첫 장은 커서 없이 부른다
- `nextCursor`를 다음 요청에 그대로 넘긴다
- `nextCursor`가 null이면 **더 안 부른다**
- 로딩 중에 또 부르지 않는다

**전송**
- 내 말풍선이 먼저 붙는다
- 답이 오면 그 아래에 붙는다
- **실패하면 내 말풍선이 남고 재시도 표시가 붙는다**
- 전송 중에는 다시 못 보낸다

**잠금**
- `meals`가 비면 입력창이 잠긴다
- 하루를 받는 동안에도 잠긴다 — 그 창에서 보내면 빈 날일 때 400을 맞는다
- **못 받았으면 잠그지 않는다** — 모르는 것을 「없다」로 단정하지 않는다

**모르는 타입**
- 모르는 `type`이 섞인 페이지를 **건너뛰고 나머지를 보여준다** — 페이지 전체가 비면 빨개진다

## 범위 밖

- **채팅에서 기록하기** — 사진·텍스트로 끼니를 남기는 것. 인식·확인·확정 흐름이 이미 있고,
  서버에도 그 API가 없다
- **카드에서 끼니 상세로 이동** — 다음 단계에 붙일 수 있지만, 채팅에서 상세로 갔다가 수정하고
  돌아오면 카드가 바뀌어 있어야 한다. 그 새로고침 경로를 먼저 정해야 한다
- **대화 삭제·검색** — 서버에 엔드포인트가 없다
- **스트리밍(타자 효과)** — 서버가 동기 응답이다
- **읽지 않은 표시·알림**
- **날짜를 채팅 안에서 자유롭게 고르기** — 앵커 칩은 오늘로 되돌리는 것만 한다. 날짜 선택기를
  넣으면 하루 화면과 진입 흐름이 두 벌이 된다

## 구현하며 이탈한 것

설계를 그대로 따르지 않은 자리와 그 이유. **판단 근거는 코드 주석에 남아 있고**, 여기에는
설계를 읽는 사람이 「구현 누락」으로 오해하지 않도록 사실만 적는다.

### 추천 질문 칩을 넣지 않았다

만들었다가 뺐다. 입력창 위 한 줄을 늘 차지하는데, 탭하면 곧바로 전송되는 문장이라 되돌릴
수도 없다. 뷰모델의 조립 로직과 테스트까지 함께 걷어냈다 — UI만 지우고 남기면 죽은 코드다.

### `createdAt`을 `Date`가 아니라 문자열로 받는다

`APIClient`의 디코더에 날짜 전략이 없어 `Date`로 받으면 숫자를 기대하다 실패한다. 이
저장소는 서버 시각을 문자열로 받아 `Date.fromISO`로 푸는 관례를 이미 갖고 있다
(`StudySession.startedAt`). 날짜 구분선에 필요한 것은 앞 10자뿐이라 시간대 변환도 거치지
않는다.

### 못 보낸 말풍선은 여러 개가 쌓인다

설계는 말풍선 하나를 전제로 썼는데, 단수로 들면 **다음 전송이 못 보낸 문장을 덮어써서**
「지우면 사용자가 다시 타이핑해야 한다」로 막으려던 상태로 그대로 돌아간다. 자리는 저장하지
않고 서버 메시지 id를 기준점으로 삼아 그릴 때 계산한다.

### 재시도를 「안전하다고 아는 것」으로만 좁혔다

`POST /diet/days/{date}/chat`은 멱등하지 않다 — 서버가 LLM을 부르고 그 결과를 저장하므로,
요청이 닿은 뒤 실패했다면 유료 호출이 이미 나갔고 대화가 저장돼 있을 수 있다. 「보내지
못했어요 · 다시 시도」를 다는 것은 `CHAT_FAILED`(서버가 저장 전에 던진다)와 요청이 나가지도
못한 연결 실패뿐이다. 그 밖의 실패는 문장만 남기고 이유를 적는다.

### 500자 상한을 앱이 먼저 막는다

서버 `@Size(max = 500)`을 넘기면 400인데, 전송 실패는 알럿을 띄우지 않아 사용자가 이유를
알 길이 없고 재시도는 같은 본문으로 영원히 실패한다. `utf16` 길이로 센다 — 서버 `@Size`가
자바 `String.length`를 보므로 문자 수로 재면 이모지가 섞였을 때 앱만 통과시킨다.

### 빈 상태·조회 실패 화면을 더했다

서버가 배포 전의 끼니·총평에는 카드를 **소급해 만들지 않아서** 배포 직후 타임라인은 정말로
비어 있다. 그때 화면이 아무 말도 하지 않으면 고장으로 읽힌다. 조회 실패도 그것과 갈라
따로 안내한다 — 알럿을 닫고 나면 둘 다 같은 빈 화면이다.
