# 식단 날짜 이동 — 하루 스와이프와 제스처 경합 설계

작성일: 2026-08-11
짝 저장소: 없음 — **서버 작업이 없다.** 앱의 제스처와 날짜 상태 문제다.

## 배경

식단 홈에서 날짜를 옮기는 길에 세 가지가 보고됐다.

1. 스트립 아래에서 좌우로 쓸어도 아무 일이 없다. **하루씩 옮겨지길 기대한다.**
2. 스트립에서 스와이프하면 탭과 겹쳐 잘 안 먹는다.
3. 주를 넘겨 날짜를 고르면 **「오늘」 버튼이 사라져 오늘로 돌아올 길이 없어진다.**

3번은 명백한 버그, 2번은 제스처 경합, 1번은 새 기능이다. **셋이 같은 코드 영역에 있고,
1번을 넣으면 2번과 똑같은 함정이 끼니 카드에서 재현되므로** 한 묶음으로 다룬다.

---

## 「오늘」 버튼 — 이름과 판단 기준이 어긋나 있다

지금 조건은 `isViewingSelectedWeek`, **보이는 주에 「선택 날짜」가 있는가**다.

```swift
if !vm.isViewingSelectedWeek {
    Button("오늘") { Task { await vm.goToToday() } }
}
```

`select(_:)`가 `visibleWeekAnchor = date`로 기준일을 선택 날짜에 맞추므로, **2주 전으로 넘겨
날짜를 고르는 순간 조건이 참이 되어 버튼이 사라진다.** 사용자는 2주 전을 보고 있는데
돌아올 버튼이 없다. 주를 한 칸씩 되짚어 오는 것 말고는 길이 없다.

버튼이 하는 일은 「오늘로 간다」이므로 판단 기준도 오늘이어야 한다.

```swift
/// 선택 날짜가 오늘이고 보이는 주에도 오늘이 있을 때만 숨긴다.
var showsTodayButton: Bool
```

`isViewingSelectedWeek`는 **그대로 둔다.** 이름이 계산하는 내용과 정확히 맞고, `DietDayTests`의
네 곳이 「기준일이 그 주로 맞춰졌다」를 확인하는 데 쓰고 있다. 틀린 것은 속성이 아니라
**그것을 버튼 조건으로 쓴 것**이다 — 화면만 새 속성으로 갈아탄다.

---

## 제스처 경합 — 버튼은 움직여도 눌린다

`Button`은 손가락이 **자기 경계 안에서** 움직였다면 떼는 순간 그냥 동작한다. 스크롤뷰가
버튼 터치를 취소해 주는 것은 **스크롤 축(세로)** 움직임뿐이라, 가로 드래그는 취소되지 않는다.

그래서 날짜 원 위에서 시작한 가로 스와이프는 「그 날짜 선택」으로 끝난다(조회까지 나간다).
동시에, 원 안에서 움직인 거리는 주 넘김 기준(50pt)에 못 미쳐 주도 안 넘어간다. **양쪽 다
안 되는 것처럼 느껴지는 이유가 이것이다.**

### 탭 제스처로 바꾼다

`Button` → `contentShape(Rectangle())` + `onTapGesture`. **탭 제스처는 손가락이 조금이라도
움직이면 스스로 취소된다.** 컨테이너의 주 넘김 `simultaneousGesture`는 그대로 둔다.

---

## 하루 스와이프 — 같은 함정이 끼니 카드에서 반복된다

스트립 아래 콘텐츠(하루 요약·점수 카드·끼니 목록)에 가로 스와이프를 붙여 하루씩 옮긴다.
판정은 스트립과 **같은 규칙**을 쓴다 — 가로 이동이 50pt를 넘고 세로의 1.5배보다 클 때만.
규칙이 다르면 손끝은 같은 동작인데 위아래에서 다르게 반응한다.

**여기서 끼니 카드가 문제가 된다.** `NavigationLink`도 버튼이므로, 카드 위에서 가로로 쓸고
떼면 **상세 화면으로 들어가면서 날짜까지 바뀐다.** 위에서 스트립에 대해 고친 것과 똑같은
결함을, 하루 스와이프를 넣는 순간 끼니 목록에 새로 만드는 셈이다.

그래서 끼니 행도 같은 방식으로 바꾼다:

| 지금 | 바꾼 뒤 |
| --- | --- |
| `NavigationLink(value: meal.id)` | `onTapGesture { selectedMealId = meal.id }` |
| `.navigationDestination(for: Int.self)` | `.navigationDestination(item: $selectedMealId)` |

`Int` 목적지를 쓰는 곳은 이 목록 하나뿐이라(`AppDestination`을 쓰는 다른 화면들과 겹치지
않는다) 값 기반 목적지를 항목 기반으로 바꿔도 다른 화면에 영향이 없다.

## 연속 스와이프는 멈춘 뒤 한 번만 조회한다

`select(_:)` 한 번은 **HealthKit 활동량 조회 + 서버 업서트 + 하루 조회**이고, 그 하루 조회가
**서버의 하루 피드백 생성을 걸어 놓는다.** 탭은 한 번씩 누르지만 스와이프는 초당 서너 번
나간다. 다섯 칸을 넘기면 왕복이 다섯 번이다.

뷰모델에 `stepDay(by:)`를 둔다.

- **즉시:** `selectedDate`·`visibleWeekAnchor`가 옮겨가고, `day`를 비우고 스피너를 켜고,
  `generation`을 올려 진행 중이던 응답을 버린다. 화면은 손끝을 바로 따라간다.
- **0.35초 뒤 한 번:** 활동량 업서트와 하루 조회. 그 사이 다음 스와이프가 오면 **예약을
  취소하고 다시 잡는다.**

**탭은 기다리지 않는다.** 날짜를 탭하면 즉시 조회하되, 예약된 스와이프 조회는 취소한다 —
안 그러면 탭으로 고른 날짜 위에 0.35초 뒤 스와이프가 겨눴던 날짜의 조회가 덮인다.

지연값은 `init`에 주입한다(`pollInterval`·`pollTimeout`과 같은 방식). 테스트가 예약을 기다릴
수 있도록 예약을 기다리는 메서드를 노출한다 — `MealConfirmViewModel.loadExistingMeals()`가
내부 `Task`를 같은 방식으로 기다리고 있어 그 관례를 따른다.

## 무엇을 테스트하나

제스처 자체는 유닛 테스트가 닿지 않는다(실기기). **판단과 상태는 전부 뷰모델에 있다.**

**「오늘」 버튼**
- 주를 넘겨 그 주의 날짜를 골라도 버튼이 **계속 보인다** (이번 버그의 재현 케이스)
- 오늘을 보고 있으면 안 보인다
- 오늘을 고른 뒤 다른 주로 넘기면 다시 보인다

**하루 이동**
- `stepDay(by: 1)`을 세 번 연속 부르면 날짜는 3일 이동하고 **하루 조회는 1회**
- 주 경계를 넘으면 `weekDates`(스트립)가 따라온다
- 예약이 걸린 상태에서 날짜를 탭하면 **예약이 취소되고** 탭한 날짜만 조회된다
- 이동 즉시 `day`가 비고 `isLoading`이 켜진다 — 이전 날짜의 끼니가 새 날짜 라벨 아래 남지 않는다

**실기기로만 확인되는 것**
- 스트립에서 스와이프해도 날짜가 안 바뀌고 주만 넘어간다
- 끼니 카드 위에서 가로로 쓸어도 상세로 안 들어가고 날짜만 바뀐다
- 끼니 카드 탭은 그대로 상세로 들어간다
